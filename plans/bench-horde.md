# 段 0.5 の測り: 50 体の骨つきの敵とパイプの密度（2026-11-04）

`make bench-horde`（組を絞るなら `BENCH_SETS="a b"`）で取り直せる。入口は普段の遊びと別の `HordeBench.main`
（`src/render/HordeBench.flix`・群れとパイプは `src/render/HordeScene.flix`）。結果は `debug/bench/horde-<組>.txt`。

## 測り方

- 機械: Apple M4 Pro（CPU 12 コア = 性能 8 + 効率 4・GPU 16 コア・メモリ 64 GB）・macOS・外付けの画面。
  窓 960×540（3D の場面も窓の画素で描く）。隠し窓（`FLIX_GE_HIDDEN`）は描き先が 480×270 に縮むので使わない。
- 場面: 最後の部屋 H の真ん中に立って東を向く。敵は部屋の床に散らばって置き、walk のクリップでプレイヤーへ歩いて寄る
  （半分ほどは背中側）。仮の敵は fps3d_lab の guard（`assets/bench/guard.glb`: ジョイント 25・三角形 7,292・材質 12 = 部品 12）。
- 1 組 = 慣らし 120 コマの後に 360 コマ。数は 2 つの道で取る:
  - **窓の前の CPU だけの測り**（nanoTime・GL なし・240 コマ）: 姿勢を作る（`pose`）と、描く物の木を組む（`plan`）
  - **窓の測り**: 1 コマの間隔（`frame#realNow` の差）と `App.withDiagnostics` の `FrameDiagnostics`
    （`submit` = GL へ送る・`swap`・`gpu` = GPU の時間・`scene3dCounts`）。`work` = 間隔 − swap（ゲームと engine の CPU の仕事の合計）
- 間隔の中央値は 6.0 ms か 12.1 ms のどちらかに寄る。画面の垂直同期（約 165 Hz と推測）に合わせて丸まるので、
  重さの比べには `work` と `submit` を使う。

## 読み取り

- **重さの大半は engine の「GL へ送る」（submit）で、draw call の数に比例する。** 骨つきの部品 1 つあたり約 8 µs
  （a と d0 の差 4.9 ms ÷ 600）。姿勢を共有しても submit は減らない（b・c は a と同じ 606 draw call で、むしろ揺れが大きい）。
  engine が骨つきの置いた物ごとに姿勢の行列を送り直すため、と推測する（engine の中は測っていない）。
- **1 体の部品（材質）を 12 → 1 にするのが一番効く。** draw call 606 → 56、work 11.9 → 6.5 ms、submit はステージだけと同じ水準。
- **姿勢の共有は CPU の姿勢の時間を 2.24 → 0.42 ms に下げる**（1 体あたり約 45 µs → 8 本だけ作る）。部品を 1 つにした後は、
  残る CPU の大きな塊なので効く（merged 6.55 → merged-shared 5.46 ms）。
- **間引き（3 コマに 1 回）は共有の後では効かない**（c も 8 本作る: 近くて前の敵が毎コマどの組も要るため）。共有なしなら
  50 → 22 本に減るが、共有の方が安くて単純。
- **GPU は 50 体（三角形 36 万）でも 1.5〜1.8 ms** で、16.7 ms に対して余裕が大きい。背中側の敵も描いている（骨つきは
  視錐台で間引かれず、置いた物 621 に対し描いた物 606）が、今は困っていない。
- **パイプはまとめれば無料に近い。** 1 区画 120 個を区画ごとに 1 つの形にすると draw call は +2 で、時間は誤差の内。
  ばらばらだと見える区画で +119 draw call・submit +1.0 ms・GPU +0.3〜0.5 ms（置いた 456 個のうち 337 個は視錐台で外れる）。
- 最大の値（30〜60 ms）は数コマだけの単発で、GC か初めて作るシェーダーと推測する（hitch.md は取っていない）。

## 決めたこと（段 2 のクリーチャーの予算と、本番に入れる手）

| 項目 | 予算・手 | 根拠 |
|---|---|---|
| ジョイント | 25 まで（計画の「20 前後」のままで良い） | 姿勢 1 本 ≒ 45 µs（25 ジョイント）。共有 8 本なら 0.4 ms |
| 1 体の材質（部品） | **1**（色は頂点の色か 1 枚の絵にベイクする。発光も同じ材質の emission で） | 部品の数がそのまま draw call と submit に効く |
| 三角形 | 1 体 7,000 前後まで（50 体で 35 万） | GPU は 1.8 ms で余裕。遠くの敵の LOD は今は要らない |
| 姿勢 | 同じクリップは時刻を **8 通り**に丸めて共有する | 2.24 → 0.42 ms |
| 間引き（3 コマに 1 回） | 入れない | 共有の後では作る本数が減らない |
| パイプ | 区画ごとに 1 つの形へまとめる（計画どおり） | ばらばらだと submit +1 ms |

本番の形（candidate）で work の中央値 5.7 ms・p95 7.5 ms。AI・パーティクル・ビューモデル・音に 10 ms ほど残る。
**エンジンに足さなくても 16.7 ms に届く見込み**なので、計画の「エンジンに足すかもしれない物」1（骨つきの物の視錐台の間引き）と
3（並列）・4（インスタンス描き）は今は相談しない。

engine へ気づいた事（足す相談ではなく、段 3 で困った時の候補）:

- 同じ姿勢の値を持つ骨つきの置いた物どうしで、姿勢の行列を送り直さない（今は共有しても submit が減らない）。
  組が 2〜4 種類・部品が 1 つの敵なら困らない見込み。
- 骨つきの物の視錐台の間引き（背中側の 15 体ほどを描かない）。GPU に余裕があるので今は要らない。

## 測っていない所

- 本物のクリーチャー（腕の長い形・2 種類のクリップの混ぜ）・ビューモデル・パーティクル・projectile・AI の重さ。段 3 で測り直す。
- Windows・GPU の弱い機械。この機械は速いので、同じ数でも余裕は小さくなる。
